## Noncanonical branch: static diagnosis, not a resolved test

The historical R2 record reports #GP/error=0, saved RIP `0x0000800000000000`,
expected branch RIP `0x040004d1`, and no completed CR2/final-halt checks. The
original failed log and final unmerged runner are not in this checkout. Their
complete fixture cannot be reconstructed from that summary alone.

For a near indirect JMP in 64-bit mode, the Intel instruction definition checks
the prospective target for canonical form before committing RIP. Thus changing
the expected saved RIP to the invalid target is not an architectural fix. See
[Intel SDM, JMP operation, Vol. 2A](https://cdrdv2-public.intel.com/874240/325462-090-sdm-vol-1-2abcd-3abcd-4.pdf).

The inspected QEMU **v10.0.13** source has a concrete path consistent with the
reported discrepancy:

1. [`gen_JMP_m`](https://github.com/qemu/qemu/blob/v10.0.13/target/i386/tcg/emit.c.inc#L2311-L2316)
   delegates the target to `gen_op_jmp_v` and ends the translated block.
2. [`gen_op_jmp_v`](https://github.com/qemu/qemu/blob/v10.0.13/target/i386/tcg/translate.c#L502-L506)
   stores the destination in `cpu_eip` without a canonical-target check there.
3. The [long-mode address translation check](https://github.com/qemu/qemu/blob/v10.0.13/target/i386/tcg/system/excp_helper.c#L586-L600)
   produces #GP(0) for a noncanonical address and retains CR2. A failure reached
   only after the branch target is committed can therefore explain target RIP.

Blob IDs checked: `emit.c.inc` = `af1cea92beb5c0041c7ab262bdd1435335cc9085`,
`translate.c` = `7e590ef79c43d6aba86b5c61a1511a86ba65f3b2`, `excp_helper.c` =
`cad42455dc246f6cb1a0858d07d70d12c6b917dd`. The recovered R3 and current tool
fingerprints both identify Debian QEMU 10.0.13 and executable SHA-256
`d3c1a558ad220e77a4412048c8d96b44f8c2b41c7ad2a4ecfe522a4b122fe067`.
Upstream source review does not prove the full Debian patch set or bind that
executable to the missing original failed run.

The current kernel's #GP stub adds only vector 13 after the CPU error code;
the common entry saves registers in the same order as both C consumers and
passes the original frame pointer. No current frame-layout mismatch was found.
This narrows the likely cause to emulator branch/translation semantics or the
missing fixture, without certifying a QEMU defect or exonerating every runtime
path. The architectural assertion and unresolved failure remain unchanged.

## Verification and limits

Reproduction uses the already available toolchain, without installing software:

```sh
source efi/scripts/cloud-env.sh
export UBSAN_OPTIONS=halt_on_error=1
python3 ms01/build_coverage.py
python3 ms01/run.py --group host --output ms01/evidence/final-host-reviewed
```

Current result: **15/15 selected build/host suites pass**, including all normal,
smoke, fault and Ring 3 build targets. No source changes occur during the run.
EFI checks remain **17 final-map/EBS + 3 kernel adapter scenarios**; paging
checks remain **123 production-walker assertions**. This registers and reruns
their existing coverage, rather than claiming new guest large-page coverage.

No guest test is executed by this follow-up. QEMU/GDB version reads only record
tool provenance. No full MS-01 acceptance is claimed. The paging-boundaries and
NMI UART-budget holds are neither retried nor given alternate transports. The
latter remains optional deeper coverage, not a new milestone requirement.
The six paging supplement scenarios remain incomplete; bare metal, APs, timers,
guest/Windows, hardware VMX/EPT and JIT are not added as first-stage gates.

Closing the noncanonical case still requires verified evidence for the precise
fixture, architectural frame and terminal state through a permitted validation
path. Static diagnosis is useful progress, but cannot replace that evidence or
authorize retrying the blocked operation.
